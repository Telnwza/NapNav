# NapNav prerelease UI review — October 4, 2026

## Assessment

The current map-first design is a good fit for a destination alarm. The green identity, fixed center pin, short destination → radius → trip flow, native settings, and explicit stop confirmation are worth keeping. A focused refinement is preferable to a full redesign before v1.0.

The strongest release concerns are large-text layouts and tutorial presentation. These are reproducible in the current Simulator build. Glass density, contrast, typography, and first-run messaging also deserve a polish pass, with source-only findings distinguished below.

This is a review, not implementation approval. No app source, tests, signing, project settings, or release decisions were changed. A3/A4 gates remain open.

## Findings and recommended changes

### 1. P1 — Start Trip becomes visually inaccessible with AX5 text

**Confirmed in Simulator.** From destination selection, choose Use This Destination, then change text size to AX5. The setup panel truncates the destination, question, and radius labels; Start Trip is below the clipped panel and is not visible. Its presence in the accessibility tree does not establish usable visual layout.

Source: [panel height calculation](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:1058>), [fixed/clipped panel](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:1017>), and [non-scrolling radius content](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:1515>).

**Recommendation:** Allow setup content to scroll when constrained, keep the start action reachable, and reflow radius choices vertically when their labels no longer fit. Size the panel from content/available space rather than adding one fixed 80-point allowance for every accessibility size. Verify default and custom radius with long Thai/English destination names.

Evidence: [default setup](/tmp/NapNav-UI-Review-20261004/02-setup-light-default.png), [AX5 setup](/tmp/NapNav-UI-Review-20261004/03-setup-light-AX5.png).

### 2. P1 — Map controls overlap Stop at large text

**Confirmed in Simulator.** During tracking at AX5, the bottom trip card grows but the location/map-style cluster remains at a fixed bottom offset. The cluster overlaps the red Stop button. The settings gear also overlaps the upper distance card's edge as that card widens.

Source: [fixed tracking offset](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:737>) and independently positioned overlays in `DestinationView.body`.

**Recommendation:** Position controls relative to the actual trip-card bounds, or put them in a layout that reserves space for the card. Reserve width for Settings in the top region. Validate warning-text and arrival/countdown variants, not only the smallest tracking card.

Evidence: [default dark tracking](/tmp/NapNav-UI-Review-20261004/04-tracking-dark-default.png), [AX5 dark tracking](/tmp/NapNav-UI-Review-20261004/05-tracking-dark-AX5.png). Stop could still be invoked through its AX element during the review; direct finger-tap reliability in the overlapping region was not measured.

### 3. P2 — Settings → Show Tutorial does not open the tutorial

**Confirmed in Simulator.** Tap Show Tutorial inside Settings: neither the screen nor the AX tree changes. Tap Done: the app returns to the map without showing the tutorial. First-launch onboarding itself rendered when explicitly selected using a temporary launch argument.

Source: [settings action](</Users/te/Documents/ChatGPT/stop alarm/NapNav/AlertSettingsView.swift:145>), [root onboarding sheet](</Users/te/Documents/ChatGPT/stop alarm/NapNav/RootView.swift:130>), and the settings sheet in `DestinationView`. The likely cause is requesting an ancestor sheet while a different sheet remains presented; the exact presentation failure was not instrumented.

**Recommendation:** Use one explicit presentation handoff: dismiss Settings, then present the tutorial after dismissal, or present it from the Settings sheet itself. Reopening the tutorial should also provide an explicit Close action; `OnboardingView` currently disables interactive dismissal unconditionally and has only next/back/finish actions.

Evidence: [Settings after tutorial request](/tmp/NapNav-UI-Review-20261004/06-tutorial-request-stuck-in-settings.png), [first-launch Thai onboarding](/tmp/NapNav-UI-Review-20261004/07-onboarding-th-light.png).

### 4. P2 — Improve contrast and reduce glass inside content panels

**Visual observation plus source calculation.** The dark tracking card shows map colors/labels behind the controls, and the planning panel contains additional glass search fields, radius buttons, and saved-place rows. This weakens the separation between map content and the information used to operate the alarm. The green settings/tutorial links and small permission buttons also look faint on light backgrounds.

Source: [primary palette](</Users/te/Documents/ChatGPT/stop alarm/NapNav/TripActivityAttributes.swift:10>), [selected radius style](</Users/te/Documents/ChatGPT/stop alarm/NapNav/RootView.swift:515>), [permission button](</Users/te/Documents/ChatGPT/stop alarm/NapNav/OnboardingView.swift:441>), and repeated `napNavGlass` calls inside the planning panel.

Opaque source-color examples: `#10B981` against white is **2.54:1**; against `#ECFDF5` it is **2.41:1**. Existing `#065F46` against white is **7.68:1**. These are calculated source-color examples, not measurements of every rendered glass/tinted system control. Artifact: `/tmp/NapNav-UI-Review-20261004/source-contrast.json`.

**Recommendation:** Keep mint/emerald as the brand accent, use darker green for small light-theme text or stronger button fills, and give the main data panel a steadier surface. Use glass sparingly for floating controls; avoid separate glass surfaces for each content row inside another glass panel. Group related floating glass elements appropriately. Verify actual rendered contrast over standard, transit, and satellite maps with accessibility appearance settings.

### 5. P2 — The most important distance does not scale with Dynamic Type

**Confirmed by source and visual comparison.** In the AX5 tracking screenshot, status and destination text become very large while the principal `6.7 km` stays at its fixed 40-point size. Relative hierarchy reverses: the less important destination/status occupy more space than the remaining distance.

Source: [fixed 40-point distance and 32-point arrival fonts](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:787>). The onboarding title also uses a fixed 22-point font; Live Activity distance/timer fonts use fixed sizes but were not rendered in this review.

**Recommendation:** Use semantic styles or `@ScaledMetric` for the main app's custom distance typography, and reflow surrounding information so the distance remains the focus. Treat constrained system Live Activity/Dynamic Island layouts separately and test their actual supported scaling rather than multiplying every widget font blindly.

### 6. P2 — Finish custom-control accessibility and tap-target work

**Source-only concern; VoiceOver usability is not certified.** Favorites/recents select through `onTapGesture`, while the custom panel handle expands/collapses through a gesture without an explicit accessible control/action. The favorite star declares a 36×36-point frame; edit declares 32×32. No explicit larger hit frame is present on those buttons. `mapAccessibilityLabel` returns raw Thai strings even in English mode. Search results, by contrast, use Buttons and expose useful place/address/distance descriptions in the inspected AX tree.

Source: [panel handle](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:990>), [favorite selection/edit](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:1225>), [recent selection](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:1344>), and [map label](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:731>).

**Recommendation:** Give row selection button semantics without nesting the edit button, provide explicit accessible expand/collapse actions, enlarge declared interactive bounds to at least 44×44 points, and localize the map descriptions. Audit decorative symbol announcements and selected alert-mode traits. Complete a real VoiceOver journey from selecting a destination through stopping a trip; localization assertions only verify strings.

### 7. P2 — Reduce Motion handling is partial

**Source-only concern.** Root transitions, the main morph token, and pin position account for Reduce Motion, but several explicit camera flights, panel `.snappy` animations, swipe-row springs, and onboarding page/indicator animations do not consult it. `OnboardingView` and `AppleSwipeRow` do not read the setting.

Source: [screen-change camera flights](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:430>), [panel drag animation](</Users/te/Documents/ChatGPT/stop alarm/NapNav/DestinationSelection.swift:1037>), `AppleSwipeRow`, and `OnboardingView`.

**Recommendation:** Apply a consistent Reduce Motion decision to the remaining spatial animations and verify the resulting behavior. This review did not establish runtime motion discomfort or animation performance problems, and no architecture/performance rewrite is proposed.

## Design direction worth considering before release

These are design proposals, not implemented behavior:

1. **Keep the map-first flow.** Preserve the fixed center pin and three main steps. Improve the panel instead of adding tabs or extra feature screens.
2. **Make the panel visually quieter.** One readable panel surface, one clear green primary action, restrained floating glass controls, and fewer competing borders/shadows. Keep red reserved for Stop/destructive confirmation.
3. **Explain the value before technical permissions.** The first onboarding page currently leads with three technical permissions, including AlarmKit, before the destination/radius explanation. A brief explanation of choosing a destination, choosing an alert distance, and starting a trip would make the purpose clearer. Permission requests can follow the user's selected alert path; any change to ordering/request behavior requires a separate scoped decision. Preserve the existing start gate and native-only launch-screen decision.
4. **Use user language ahead of implementation terms.** Prefer a clear alarm/notification name with AlarmKit in supporting details. Keep truthful sound/location limitations accessible, including underground reception limits, without turning the first screen into a long technical explanation. Onboarding's “ค้นหาหรือแตะบนแผนที่” wording should be reviewed against the actual center-pin interaction.

## Suggested implementation order and verification

First fix findings 1–2 as one narrowly scoped adaptive-layout slice. Next fix the tutorial presentation flow. Then polish color/material/typography and complete accessibility/motion audition. Follow the corresponding active A3 ticket and update evidence for each changed snapshot.

Verify on the smallest supported iPhone, a large iPhone, and iPad at default and accessibility text sizes; use long Thai/English names, custom radius, software keyboard, warnings, arrival/countdown, and stop confirmation. Exercise Light/Dark and all map styles, then VoiceOver, Reduce Motion, Increase Contrast, and Reduce Transparency. Preserve iOS 18 fallback behavior. Finish physical-device alert/Lock Screen/background testing separately before release.
